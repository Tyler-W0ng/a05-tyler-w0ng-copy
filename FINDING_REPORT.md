# Vulnerability finding reports (A05, A06)

For each candidate vulnerability your pipeline identifies, it produces a
structured report. The report is not simply a statement that a
vulnerability exists. It must give an independent analyst, or an
independent agent, enough evidence to understand, reproduce, and validate
the finding.

**A report is a claim accompanied by evidence.** Statements or conclusions
generated by an LLM are not, by themselves, evidence of a vulnerability.
The discovery agent's conclusion is not ground truth: a finding is as strong
as the quality, reproducibility, and independence of its evidence.

A good report lets an evaluator answer four questions:

1. Where is the bug?
2. Why is it a bug?
3. Why does it have security implications?
4. Can I reproduce it independently?

---

## 1. Layout

```text
output/items/<target-id>/
    summary.json                  what was analyzed, and how it went
    findings/
        finding-001/
            report.json           the machine-readable report (§3)
            REPORT.md             optional human-readable version
            artifacts/
                replay/Dockerfile the automated reproduction (§4)
                poc.bin
                sanitizer.txt
                ...
        finding-002/
            ...
```

`summary.json` is written for every target, including targets with no
findings or where analysis failed:

```json
{"target": "t-03", "status": "completed", "findings": ["finding-001"],
 "notes": "built with ASan; 40 min of fuzzing on 3 harnesses"}
```

`status` is `completed`, `failed` (with the reason in `notes`), or
`timeout`. "No findings" means no vulnerability was demonstrated within your
analysis. It does not mean the target is safe.

## 2. What a report contains

**Target identification.** The repository URL, the exact Git commit, the
build configuration, the platform or environment when relevant, and any
configuration options needed to expose the vulnerability. An evaluator must
be able to obtain exactly the code you analyzed.

**Vulnerability summary.** A short descriptive title. A description that
explains the vulnerability rather than its symptoms: "the program crashes on
this file" is not enough. The vulnerability type, the CWE identifier when
applicable, the estimated severity, and your confidence.

**Location.** The source file, function, line range, and component, as
precisely as reasonably possible.

**Root cause.** Why the vulnerability occurs: the attacker-controlled input,
the relevant sources and sinks, the data or control flow leading to the
vulnerable operation, the missing or incorrect validation, and the security
property or invariant that is violated. Distinguish the observed symptom
from the underlying bug.

**Evidence.** Concrete support for the claim: sanitizer or Valgrind
reports, triggering inputs, fuzzer output, stack traces, static-analysis
results, data-flow traces, assertion failures, debugger output, relevant code
excerpts, and tests demonstrating the incorrect behavior. Prefer evidence
obtained by executing the program or by independent tools. Store large items
as separate artifacts and reference them, with their SHA-256.

**Reproduction.** Instructions to reproduce the finding from a clean checkout
of the specified commit: build commands, dependencies and environment,
configuration, the triggering command and input files, and the expected
observable result. Example:

```text
Build:    CC=clang CFLAGS="-fsanitize=address -g" make
Execute:  ./parser artifacts/poc.bin
Expected: AddressSanitizer reports a heap-buffer-overflow in parse_header()
```

The same reproduction must also be **automated** (§4).

**Security impact.** Why this is a security vulnerability and not just a
defect: whether an attacker controls the input, the preconditions and
required privileges, the security boundary crossed, and the effect on
confidentiality, integrity, or availability. Avoid unsupported claims: a
memory-corruption bug is not "arbitrary code execution" unless the evidence
shows it.

**Validation.** What was done to verify the finding independently: whether
it reproduced and how many times, the tools and methods used, the attempts
to rule out false positives, and whether validation was independent of the
agent or method that found it. Classify the finding in one of four states:

| State | Meaning |
|---|---|
| `candidate` | the pipeline identified a potentially vulnerable condition |
| `reproducible` | the reported behavior can be reliably reproduced |
| `confirmed_bug` | analysis confirms the behavior results from an actual defect |
| `confirmed_vulnerability` | the defect is reproducible and has a justified security impact |

Do not classify a finding as a confirmed vulnerability only because the
program crashes.

**Logic (A06 only).** The rule of the specification that is violated (its
ID and text), the initial state, the ordered sequence of interactions, the
expected behavior according to the specification, and the observed
behavior.

## 3. `report.json`

`report.json` follows the JSON Schema your repository carries as
`.cs279/finding.schema.json`. The preflight check validates it. Abridged:

```json
{
  "schema_version": "cs279-finding/1",
  "id": "finding-001",
  "target": {"repository": "https://github.com/example/parser", "commit": "<40 hex>",
             "build": "CC=clang CFLAGS='-fsanitize=address -g' make", "platform": "linux/amd64",
             "configuration": "default"},
  "finding": {"title": "...", "description": "...", "type": "heap buffer overflow",
              "cwe": ["CWE-122"], "severity": "high", "confidence": "high"},
  "location": [{"file": "src/header.c", "function": "parse_header",
                "line_start": 210, "line_end": 231, "component": "header parser"}],
  "root_cause": {"input": "...", "source": "...", "sink": "...", "flow": "...",
                 "missing_check": "...", "violated_property": "..."},
  "evidence": [{"kind": "sanitizer", "path": "artifacts/sanitizer.txt",
                "sha256": "<hex>", "description": "..."}],
  "reproduction": {"steps": "...", "expected": "...",
                   "replay": {"context": "artifacts/replay",
                              "expect": {"stderr_regex": "AddressSanitizer: heap-buffer-overflow"}}},
  "impact": {"attacker": "...", "preconditions": "...", "privileges": "none",
             "boundary": "...", "confidentiality": "low", "integrity": "high",
             "availability": "high", "consequences": "..."},
  "validation": {"state": "confirmed_vulnerability", "attempts": 5, "reproductions": 5,
                 "methods": ["..."], "false_positive_checks": "...", "independent": true},
  "logic": null
}
```

## 4. Automated replay

The grader reproduces every finding you classify as `reproducible` or
higher. It does not trust your logs.

**A05: target-side replay.** `reproduction.replay.context` is a directory
with a `Dockerfile` that checks out the target at the reported commit,
builds it as needed, and has the trigger as its default command. The grader
builds the image (with network access), runs it **without** network access
under a 5-minute limit, and checks the result against `expect`. `expect`
contains any of `exit_code` (an integer, or `"nonzero"`), `stdout_regex`,
and `stderr_regex`, and all of them must match.

**A06: client-side replay.** `reproduction.replay.context` is a directory
with a `Dockerfile` for a client that performs the interaction sequence
against the service at `TARGET_HOST`:`TARGET_PORT`. The grader starts a
fresh instance of the target, runs your client, and checks the target's
state independently. Your `expect` is not used.

Each replay runs three times. A finding replays successfully if at least
two runs succeed.
